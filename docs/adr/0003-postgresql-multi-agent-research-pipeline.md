# ADR-0003：使用 PostgreSQL 租约队列承载多 Agent 策略研发流水线

## 状态

Accepted

## 日期

2026-08-18

## 背景

原型系统运行于本地 SQLite，策略生成是一条请求内的单模型调用。新系统需要长时间运行、崩溃恢复、严格阶段隔离、模型成本上限、真实历史数据缓存以及可审计的验证记录。生产环境已确定为自有 Linux 服务器。

## 决策

1. 生产使用 Node Web、PostgreSQL 16+ 和独立 Node Worker。
2. PostgreSQL 同时作为业务数据库、行情缓存和任务队列；Worker 通过带过期时间的租约列和 `FOR UPDATE SKIP LOCKED` 领取任务，不引入 Redis。
3. 旧 SQLite 数据在维护窗口一次性迁移，逐表核对行数与关键字段哈希；不长期双写。
4. 编排器是固定状态机，Agent 只能提交结构化结果。评分、回测和准入均为确定性代码。
5. 新流程由默认关闭的功能开关先向管理员开放；旧单 Agent 接口单独安排废弃。

## 备选方案

### Redis/BullMQ 队列

- 优点：成熟的延迟任务、重试和监控生态。
- 缺点：增加一个需要备份、监控和故障处理的状态系统，任务结果与业务事务无法原子提交。
- 结论：首期拒绝；当前吞吐不需要额外基础设施。

### 继续使用 SQLite + 定时请求

- 优点：改动较小。
- 缺点：不适合目标 Linux/Node 部署，缺少所需行级并发领取语义，长任务恢复和本地 Worker 运维复杂。
- 结论：拒绝。

### 请求内同步多 Agent

- 优点：实现简单。
- 缺点：超时、断线即丢失、无法取消和恢复，用户等待时间不可接受。
- 结论：拒绝。

## 影响

- 需要 PostgreSQL schema、迁移/核验工具、独立 Worker 启停脚本和生产环境变量。
- 任务阶段与事件持久化使断线恢复、审计和成本控制成为可能。
- PostgreSQL 成为单一生产真源；切换前必须完成演练和可回滚备份。
- 功能开关存在期间要维护新旧两条生成入口，但不允许两套策略验证标准并存。

## 安全与隐私

- 模型密钥使用现有主密钥派生的 AES-GCM 加密保存；Worker 仅在调用时解密。
- 客户 API 永不返回供应商、Base URL、Key 或隐藏提示词。
- 角色输出不包含隐藏推理，仅包含公开结论、数据引用和异议。
