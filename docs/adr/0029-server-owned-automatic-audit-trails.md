# ADR-0029：服务端拥有自动审计事实，用户不填写通用审计原因

状态：Accepted

日期：2026-08-30

## 背景

历史上为减少确认弹窗，普通配置和控制操作改成页面内填写审计原因。结果是审计完整性依赖用户自由文本，按钮
又被 3–500 字校验阻塞。模型连接测试可以成功，但 Profile 保存按钮仍因缺少原因不可用；相同模式已扩散到
集成、配置版本、权限、账号和发布控制。

自由文本不能证明“谁在何时对哪个对象执行了什么动作”，还会产生复制粘贴、无意义占位和潜在敏感信息落日志
的问题。可信审计事实本来就能从认证会话、服务端动作目录、资源标识、事务结果和请求关联信息确定。

## 决策

1. 通用审计输入从三端 UI 和新请求中移除，按钮不再依赖审计文字。
2. 服务端使用 allowlisted action 生成 `automatic:<action>` 兼容标记，并记录 actor、subject、request/trace、
   幂等和结果。
3. 旧 API 可暂时接受 `reason`，但忽略它，防止旧客户端自由文本成为审计真源。
4. 既有 `reason` 列和历史记录不删除；自动标记满足非空旧约束并提供无损回滚路径。
5. 资金依据、拒绝说明、事故说明、风控处置和 PII 访问用途属于业务决定，不属于通用审计输入，继续保留。
6. 高风险确认、recent MFA、maker/checker、权限、状态机、幂等和追加式事实保持不变。

## 后果

收益：合法操作不会被无意义文字阻塞，审计来源可验证，旧 API 可平滑迁移，秘密或个人数据被误填进审计的概率
下降。

代价：兼容期内部分 `reason` 字段显示机器标记；业务原因与审计元数据必须在 UI/API 命名上明确区分。未来若
移除旧列，需要另行加法迁移和数据保留评审。

## 被拒绝的方案

- 自动预填一个可编辑原因：仍允许浏览器篡改审计来源，也保留无意义输入。
- 仅放宽最小长度：按钮问题减轻，但审计责任仍错误地落在用户身上。
- 立刻删除所有 `reason` 列：破坏旧 API、不可变事实和回滚能力。
- 删除所有业务说明：会损害资金、风控、合规和拒绝决定的可解释性。
