## 4. 镜像交付

### 4.1 官方 CI 制品

tag workflow 使用 `deploy/container/Dockerfile` 构建并发布四张版本化 GHCR 镜像，同时生成 SBOM、provenance 和 digest 证据。四个 matrix build、身份校验和 manifest job 均成功。

### 4.2 目标主机构建

目标主机本次未配置 Registry 凭证，因此没有在服务器登录 GHCR。服务器从精确 tag/commit 的临时 checkout，使用以下共同约束构建四张 `linux/amd64` 镜像。以下是参数模板，尖括号项必须按镜像替换，不能原样执行：

```bash
docker buildx build \
  --file deploy/container/Dockerfile \
  --platform linux/amd64 \
  --target <web|runtime> \
  --build-arg RIVERTON_RELEASE_TAG=v1.0.0-beta.2 \
  --build-arg GIT_COMMIT_SHA=5b7e2b063800b9c7c2e40159893650035ff20cc5 \
  --build-arg RIVERTON_APP_AUDIENCE=<client|operations|maintenance> \
  --build-arg RIVERTON_APP_HOST=<对应正式域名> \
  --label org.opencontainers.image.version=v1.0.0-beta.2 \
  --label org.opencontainers.image.revision=5b7e2b063800b9c7c2e40159893650035ff20cc5 \
  --load \
  --tag <版本化镜像引用> \
  .
```

Runtime target 不传 audience/host build argument。构建后使用 `docker image inspect` 读取实际 image ID，并按仓库发布算法计算聚合 artifact SHA-256，写入只读 release manifest。

### 4.3 本次发现的构建辅助脚本缺陷

`npm run release:build-images` 对应的 `scripts/release/build-container-images.mjs` 当前没有向 `docker buildx build` 传入 `--file deploy/container/Dockerfile`，而仓库根目录没有 `Dockerfile`。因此该命令从仓库根目录运行会失败；本次没有通过创建根目录 Dockerfile 或改写历史来绕过，而是使用上面的显式 Dockerfile 命令完成构建。

在修复脚本并补充参数合同测试前：

- 官方首选路径是 tag 触发的 container workflow；
- 服务器本地构建必须显式传入 `--file deploy/container/Dockerfile`；
- 不得在 Runbook 中把 `npm run release:build-images` 写成已验证可用。

- 容器未向宿主机发布数据库端口。

- migration registry 最后版本为 `0042_udun_deposit_gateway.sql`。
- 所有已应用 migration checksum 保持一致。

### 6.2 数据库角色策略

第一次从 Compose 工具容器运行 role policy 时被安全策略拒绝，因为该工具只接受 loopback 地址，而 Compose 内数据库主机名是 `postgres`。这不是数据库权限失败，也没有通过放宽校验解决。

最终做法是在 SSH 会话内建立一次性、仅 loopback 监听的端口转发，通过本机回环地址运行同一只读策略检查；凭证只在受控进程内传递，不写入命令输出、文件或文档。结果：

```json
{
  "database": "agentnovas",
  "findings": []
}
```

检查完成后立即移除临时转发。后续应为容器部署增加受支持的 role-policy 执行包装器，同时保留“只允许 loopback、不在日志暴露口令”的安全边界。

8. 验证完成后原子更新 `current` 和 `previous` 符号链接。
